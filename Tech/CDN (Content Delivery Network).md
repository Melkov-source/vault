**CDN** — это сеть геораспределённых серверов, обеспечивающая быструю доставку контента пользователю. Контент (изображения, скрипты, страницы и пр.) отдается с ближайшего к пользователю узла, что снижает задержки, уменьшает нагрузку на основной сервер и повышает отказоустойчивость.

Основные принципы работы:
- Кэширование ресурсов на edge-серверах;
- Маршрутизация запросов к ближайшему географически узлу;
- Edge computing — выполнение логики прямо на CDN-узле.

### Настройка Cloudflare
1. Домен и DNS
	1. Подключение домена к Cloudflare
	   Нужно указать Cloudflare как DNS-провайдера у регистратора, заменив NS-записи. Это необходимо сделать, чтобы Cloudflare мог работать полноценно с DNS
	   
	2. DNS-записи
	   Нужно создать `A` или `CNAME` записи, указывающие на origin-сервер.
	   В нашем случае мы использовали обычный статичные сервер, настроенный через Caddy, в котором предварительно прописаны все заголовки для разных MIME типов файлов - для компрессии и для кеширования (TTL Browser)
	   
2. Кэширование
	1. Cache Rules
	   Необходимо создать правила, которые будут говорить всем точкам присутствия какие ресурсы должны кэшироваться и каким образом. Там можно сделать условия реагирования правил по маршрутам, домену и т.д. Указать определение заголовков кэширования как на Browser стороне, так и на Edge. 
	   
	   На проекте мы сделали так, чтобы кэширование брало все настройки с origin-сервера. Он отдает `Cache-Control`, `ETag`, `Content-Encoding`, `Content-Type` корректно и не мешает Cloudflare кэшировать через заголовки (`Vary`, `Authorization`, `Set-Cookie`). А для edge серверов настроено через правило.
	   
	   Так же мы кэшируем все статичные данные, кроме главной страницы /index.html, дабы она бралась с origin-сервера и была всегда актуальной.
	   
	   После настройки, контент можно получить и посмотреть у него `CF-Cache-Status` в заголовках, в котором у всех ресурсов полученных через кэш сервер (точку присутствия) будет значение `HIT`. Если же там что-то другое, например `MISS` или `Bypass` - это значит, что контент был получен не с ближайшей точки, а прямиком из orign-сервера.
	   
	2. Page Rules
	   Для того чтобы все корректно работало на разных уровнях кэширования, нужно настроить глобальные правила для всей страницы. Например установить Cache Level в Cache Everything, чтобы CDN мог обрабатывать любые типы файлов.
	   
3. Компрессия
   По умолчанию CDN сжимает ресурсы, которые не имеют заголовков о том, что они имею какую-то компрессию. Это нужно для передачи ресурсов на точки присутствия.
   
   Далее эти заголовки сохраняются или могут быть переопределены через скрипты на этих точках. Например можно создать worker, который будет перед тем как отдать пользователю ресурс - дополнительно редактировать заголовки или что-то еще.
   
   Если на точке присутствия у ресурса нет настроек компрессии, то пользователю он будет упакован в один из допустимых для него форматов (клиент вместе с запросом передает заголовок со списком разрешенных форматов).
   
   На текущем проекты мы делали настройку компрессии предварительно еще на этапе отдаче ресурса с origin-сервера. Это настроено в Caddyfile. Таким образом точки присутствия его дополнительно не сжимают и передают в том виде в которым им вернул сервер. (в Compressions Rules могут быть дополнительные настройки сжатия на этапе передачи из точки к конечному пользователю, по умолчанию они отсутствуют)
   
4. Проксирование
   Для того чтобы настроить передачу ресурсов из точек присутствия к конечному пользователю, Cloudflare должен понимать откуда брать ресурсы. Это можно сделать несколькими подходами.
	1. Прокси сервер
	   Это обычный сервер, например написанный на Node.js или же более глобально созданный через Nginx или Caddy. Его задача заключается в подготовки ресурса к отдаче на запрос.
	    
	2. Worker
	   Это обычный скрипт, выполняющийся на каждый запрос пользователя к конечной точке определенной через Anycast (система маршрутизации и адресации). В этом скрипте можно указать откуда брать ресурсы. Например с кастомного прокси сервера, потом дополнительно его настроить и отдать пользователю.
	   
	   Мы его использовали для того чтобы перенаправлять ресурсы с нашего Caddy сервера, дабы не настраивать контент в worker и не мучаться с компрессией, которая накладывалась через R2 хранилище объектов.
	   
	   Так же от него можно избавиться, но для этого нужно указать напрямую в DNS в CNAME записи в качестве таргета origin-сервер.
