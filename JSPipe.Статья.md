# Unity WebGL без боли: модули, packets и TypeScript bridge

## Что добавить перед публикацией

Чтобы статья стала более убедительной, перед публикацией стоит добавить реальные материалы из проекта:

- короткий фрагмент настоящего `upackage.json`;

- скриншот структуры проекта;

- ссылку на страницу ассета в Unity Asset Store.

## Вступление

Unity WebGL сначала кажется почти магией. Берешь Unity-проект, выбираешь WebGL, нажимаешь Build, получаешь страницу, открываешь в браузере - и твой C#-мир внезапно живет внутри web-страницы.

Первые несколько минут это действительно приятно.

А потом почти всегда появляется задача, которая напоминает: WebGL - это не просто еще одна платформа Unity. Это браузер.

Нужно вызвать SDK аналитики. Или авторизовать пользователя через web API. Или открыть wallet provider. Или сходить в IndexedDB. Или встроить Unity в уже существующий frontend. Или просто дернуть npm-пакет, потому что в JavaScript-мире нужная библиотека уже давно написана, протестирована и используется половиной интернета.

И тут выясняется странная вещь: Unity уже находится в браузере, JavaScript буквально рядом, но нормальная коммуникация между C# и современным TypeScript/npm-кодом ощущается не как мост, а как набор узких технических лазеек.

Из этой боли у меня и вырос JSPipe - bridge для Unity WebGL, который позволяет общаться между C# и TypeScript более предсказуемо: через модули, сообщения, request/response и нормальную сборку TS/npm-кода.

Эта статья не про то, как нажимать кнопки в ассете. Она про то, почему такой мост вообще понадобился и какие решения оказались важными.

## Как Unity предлагает общаться с JavaScript

Обычный путь в Unity WebGL выглядит примерно так.

На стороне C#:

```csharp
using System.Runtime.InteropServices;
using UnityEngine;

public class BrowserBridge : MonoBehaviour
{
    [DllImport("__Internal")]
    private static extern void TrackEvent(string eventName);

    public void SendEvent()
    {
        TrackEvent("level_started");
    }
}
```

На стороне `.jslib`:

```javascript
mergeInto(LibraryManager.library, {
  TrackEvent: function (eventNamePtr) {
    const eventName = UTF8ToString(eventNamePtr);
    window.analytics.track(eventName);
  }
});
```

Для простого случая это нормально. Честно говоря, для простого случая это даже хороший механизм: прямой, явный, без лишней инфраструктуры.

Проблема начинается не с первого вызова. Проблема начинается с пятого.

Один метод отправляет событие в аналитику. Второй ждет результат от SDK. Третий должен передать объект. Четвертый получает ошибку из `Promise`. Пятый работает только после того, как загрузился внешний script. Шестой нужен не в runtime Unity, а в HTML-шаблоне до запуска WebAssembly.

Через некоторое время `.jslib` перестает быть тонким glue-кодом и становится местом, где случайно поселилась архитектура.

## Почему `.jslib` быстро становится тесно

Я не считаю `.jslib` плохим. Он решает свою задачу: дает Unity возможность встроить JavaScript в WebGL-билд.

Но у него есть важная особенность: это низкоуровневый механизм. Он не пытается быть приложенческим протоколом. Он не знает, что такое модуль авторизации, async handler, npm-зависимость, типизированный payload или ошибка, которую надо вернуть в C#.

Когда проект растет, появляются типичные симптомы:

- глобальные функции множатся без общей структуры;
- данные гоняются строками;
- JSON-сериализация размазывается по коду;
- `Promise` превращается в callback id;
- ошибки остаются в browser console;
- npm-пакеты подключаются через обходные пути;
- порядок инициализации становится хрупким;
- frontend-сборка живет отдельно от Unity build.

Отдельно неприятно, что многие ошибки всплывают поздно. Не в IDE. Не при компиляции. А уже после WebGL build, в браузере, иногда только в production-окружении.

В какой-то момент я сформулировал проблему для себя так: мне не нужен еще один helper для вызова JavaScript. Мне нужен нормальный канал связи между двумя runtime.

## Не “вызвать функцию”, а “передать сообщение”

Когда C# и JavaScript общаются редко, удобно мыслить функциями:

```text
C# вызывает JS-функцию
```

Но когда таких взаимодействий становится много, лучше думать иначе:

```text
Unity runtime и browser runtime обмениваются сообщениями
```

Это меняет архитектуру.

Появляется не набор отдельных мостиков, а транспорт:

```text
request id
module name
method name
payload
response
error
```

Условный вызов начинает выглядеть не как "найди глобальную функцию", а как пакет:

```json
{
  "id": "42",
  "module": "Analytics",
  "method": "Track",
  "payload": {
    "Event": "level_started",
    "Level": 3
  }
}
```

Ответ тоже становится частью протокола:

```json
{
  "id": "42",
  "ok": true,
  "result": null
}
```

А ошибка перестает быть случайной строкой в console:

```json
{
  "id": "42",
  "ok": false,
  "error": {
    "code": "SDK_ERROR",
    "message": "Analytics SDK is not initialized"
  }
}
```

Это простая идея, но она сильно меняет ощущение от разработки. Ты больше не прокладываешь отдельную дырку для каждого вызова. Ты строишь общую трубу.

## Модули вместо глобальной свалки

Следующий вопрос: как не превратить один общий bridge в один большой `window.UnityBridge`?

В JSPipe я пришел к модульной модели. Модуль существует на обеих сторонах - в C# и в TypeScript - и синхронизируется по имени.

Например, есть модуль `Greeting`.

На стороне Unity:

```csharp
using Cysharp.Threading.Tasks;
using TiltShift.JsPipe;
using UnityEngine;

public class GreetingModule : JSPipeModule
{
    public override string Name => "Greeting";

    public GreetingModule()
    {
        RegisterHandler<NameRequest>("SayHello", OnSayHello);
    }

    private void OnSayHello(NameRequest req)
    {
        Debug.Log($"Hello from JS: {req.Name}!");
    }

    public async UniTask<string> GetUserName()
    {
        var response = await Call<NameResponse>("GetName");
        return response.Name;
    }

    private class NameRequest
    {
        public string Name { get; set; }
    }

    private class NameResponse
    {
        public string Name { get; set; }
    }
}
```

На стороне TypeScript:

```ts
import { JSPipeModule } from "./jspipe/JSPipeModule";

class GreetingModule extends JSPipeModule {
  constructor() {
    super("Greeting");

    this.registerHandler("GetName", () => {
      return { Name: "Player" };
    });
  }

  public sayHello(name: string): void {
    this.notify("SayHello", { Name: name });
  }
}

new GreetingModule().sayHello("Unity");
```

Здесь есть несколько важных решений.

Во-первых, имя модуля становится частью контракта. `"Greeting"` на C# и `"Greeting"` в TypeScript - это не случайность, а точка синхронизации.

Во-вторых, методы живут внутри модуля. Не просто `GetName`, а `Greeting.GetName`. Это сразу дисциплинирует структуру проекта.

В-третьих, у коммуникации есть два разных намерения:

- `Notify` - отправить событие и не ждать ответа;
- `Call` - отправить запрос и дождаться результата.

Это кажется мелочью, но в реальном коде она спасает от каши. По вызову сразу видно, что происходит: событие или request/response.

## Async - место, где мосты обычно начинают скрипеть

Самый простой bridge почти всегда проходит демо:

1. C# вызвал JavaScript.
2. JavaScript вернул строку.
3. Unity вывела `Debug.Log`.

А потом приходит настоящий web.

В JavaScript почти все интересное асинхронно: `fetch`, SDK, popup авторизации, wallet connection, IndexedDB, платежи. Даже если API выглядит простым, внутри часто живет `Promise`.

На TypeScript стороне хочется писать обычный async-код:

```ts
this.registerHandler("VerifyLogin", async (payload: LoginRequest) => {
  const response = await fetch("/api/session/verify", {
    method: "POST",
    headers: {
      "Content-Type": "application/json"
    },
    body: JSON.stringify(payload)
  });

  if (!response.ok) {
    throw new Error(`Session verification failed: ${response.status}`);
  }

  return await response.json();
});
```

На C# стороне хочется так же спокойно ждать результат:

```csharp
try
{
    var profile = await authModule.Call<UserProfile>(
        "VerifyLogin",
        new
        {
            UserId = userId,
            Token = token
        }
    );

    ApplyProfile(profile);
}
catch (Exception exception)
{
    Debug.LogError(exception);
    ShowLoginError();
}
```

Чтобы это работало, bridge должен делать скучную, но важную работу: присваивать запросу id, хранить pending-вызов, маршрутизировать пакет, дождаться ответа, завершить `Task`/`UniTask`, а при ошибке не проглотить ее.

Именно это скучное место лучше иметь в инфраструктуре, а не заново изобретать для каждой интеграции.

## TypeScript нужен не ради красоты

Я люблю C#, но в браузере есть своя реальность. Большая часть browser SDK, документации и примеров живет в JavaScript/TypeScript/npm-мире.

Можно пытаться спрятать это за `.jslib`, но тогда web-часть проекта постепенно становится не web-кодом, а набором вставок, которые сложно проверять, собирать и сопровождать.

TypeScript в этой задаче важен как способ вернуть web-коду нормальную среду:

- импортировать npm-пакеты;
- описывать payload;
- ловить ошибки на стороне TS до запуска WebGL;
- разделять код по модулям;
- использовать привычный bundler;
- не писать всю логику в одном `.jslib`.

Например, если хочется использовать npm-пакет для валидации:

```ts
import { z } from "zod";

const PurchaseRequest = z.object({
  ProductId: z.string(),
  Quantity: z.number().int().positive()
});

this.registerHandler("ValidatePurchase", async (payload: unknown) => {
  const request = PurchaseRequest.parse(payload);

  return {
    ProductId: request.ProductId,
    Quantity: request.Quantity,
    Valid: true
  };
});
```

Это обычный frontend-код. И в этом его ценность.

Unity WebGL уже работает в браузере. Значит, было бы странно не использовать зрелую браузерную экосистему.

## Но runtime-моста мало

На этом месте легко сделать ошибку: решить, что достаточно написать API для сообщений.

На практике половина боли живет не в runtime, а в сборке.

Если TypeScript собирается отдельно, npm-зависимости ставятся вручную, WebGL template меняется руками, а `.jspre` копируется как придется, проект быстро становится хрупким. Особенно если над ним работают Unity-разработчик и frontend-разработчик одновременно.

Поэтому в JSPipe я сделал не только runtime-слой, но и build flow.

В проекте появляется `upackage.json`. В нем описаны две важные точки входа:

- `template` - код, который попадет в HTML-шаблон и выполнится до запуска Unity;
- `main` - код, который собирается в `.jspre` и живет рядом с Unity/WebAssembly runtime.

Это разделение оказалось важнее, чем кажется.

Есть JavaScript страницы: подготовить wrapper, повесить обработчики, настроить ранний UI, сделать что-то до загрузки WebAssembly.

А есть JavaScript bridge-слоя: зарегистрировать модули, подключить npm SDK, общаться с Unity runtime.

Если не разделять эти два мира, порядок инициализации начинает превращаться в лотерею.

## HTML template тоже часть архитектуры

Unity WebGL template часто воспринимают как декоративную оболочку: логотип, прогрессбар, CSS, maybe fullscreen button.

Но в реальных web-проектах template - это место, где начинается приложение. Там может жить ранний bootstrap, интеграция с outer page, подготовка окружения, загрузка вспомогательных scripts.

JSPipe берет этот участок под контроль: исходный шаблон лежит в `Assets/JSPipeTemplate`, а перед WebGL build генерируется рабочий Unity template. TypeScript из `template` entry point собирается, получает hash в имени файла и вставляется в `<head>`.

То есть вместо ручного "не забудь подключить этот скрипт" получается повторяемый процесс.

Это не самая эффектная часть ассета, но для меня она одна из самых важных. Потому что стабильный build pipeline часто экономит больше времени, чем красивый runtime API.

## Как выглядит сборка в общих чертах

Я не хочу превращать статью в инструкцию по меню, поэтому опишу только идею.

Перед WebGL build JSPipe делает две вещи:

1. Собирает `main` entry point через `esbuild` в `JSPipe.jspre`.
2. Собирает `template` entry point, вставляет получившийся script в WebGL template и назначает этот template для сборки.

После build временные артефакты удаляются.

Смысл в том, что TypeScript/npm-часть не должна быть ручным довеском к Unity. Она должна быть встроена в тот же build lifecycle.

В этом месте особенно хорошо проявляется отличие "библиотеки с парой функций" от "интеграционного слоя". Если runtime API отличный, но build каждый раз требует ручной магии, боль просто переезжает в другое место.

## Ошибки, логирование и наблюдаемость

Еще один урок: bridge без диагностики быстро становится черным ящиком.

Когда сообщение не дошло, хочется понять:

- модуль не зарегистрирован?
- method handler не найден?
- payload не распарсился?
- JS handler упал?
- C# сторона не дождалась ответа?
- ошибка произошла до запуска Unity?

Поэтому в JSPipe пакеты можно перехватывать на уровне модуля через `OnRxPacket`.

Например, можно добавить логирование и метрики:

```csharp
public override void OnRxPacket(JsPipePacket packet)
{
    Debug.Log($"[{Name}] Received: {packet.Id}");

    if (packet.Request != null)
    {
        Analytics.Track("rpc_request", packet.Request.Method);
    }

    base.OnRxPacket(packet);

    if (packet.Response?.Error != null)
    {
        HandleError(packet.Response.Error);
    }
}
```

Это не выглядит как killer feature, пока проект маленький. Но когда через bridge начинают ходить авторизация, платежи, аналитика и события интерфейса, возможность посмотреть на поток сообщений становится очень полезной.

## Где этот подход особенно полезен

Такой bridge не нужен каждому Unity WebGL проекту.

Если у вас маленькая игра, которая почти не общается с браузером, один `.jslib` может быть проще и лучше. Я вообще не люблю тащить инфраструктуру туда, где хватает трех строк.

Но есть классы проектов, где нормальный interop быстро окупается:

- 3D-конфигураторы товаров;
- Unity WebGL внутри большого frontend-приложения;
- browser games с авторизацией, аналитикой и платежами;
- образовательные симуляторы внутри LMS;
- web3/wallet-интеграции;
- проекты, где Unity отвечает за визуализацию, а бизнес-логика живет в web/backend-экосистеме;
- прототипы, где нужно быстро подключать существующие npm SDK.

В таких проектах Unity - не остров. Это часть web-приложения. И граница между Unity и браузером становится полноценным архитектурным элементом.

## Компромиссы

Конечно, мост между C# и TypeScript не превращает WebGL в нативную платформу.

Остаются ограничения:

- все данные на границе сериализуются;
- большие payload требуют аккуратности;
- browser API зависят от HTTPS, user gesture, iframe policies и permissions;
- WebGL build сложнее отлаживать, чем Editor;
- в Editor нужен mock-слой, если хочется тестировать без браузера;
- типы C# и TypeScript все равно нужно синхронизировать дисциплиной или генерацией;
- порядок инициализации остается важным.

Но хороший bridge не обязан уничтожить всю сложность. Он должен собрать ее в одном месте и дать разработчику понятную модель.

Для меня это и есть главный критерий: стало ли меньше случайной магии?

## Что я бы развивал дальше

Самое очевидное направление - контракты.

Сейчас модульная модель уже дисциплинирует код: есть имя модуля, имя метода, payload, response. Но форму payload все еще нужно синхронизировать между C# и TypeScript.

Хочется прийти к одному из вариантов:

- генерировать TypeScript-типы из C# DTO;
- генерировать C# DTO из TypeScript schemas;
- использовать общий schema layer;
- добавить devtools-панель для просмотра сообщений;
- сделать удобный mock-runtime для Editor;
- гонять bridge-тесты в headless-браузере.

Особенно интересна devtools-часть. У bridge есть естественный поток пакетов, а значит его можно визуализировать: кто кого вызвал, сколько ждал, где упал, какой payload ушел.

## Вывод

Unity WebGL - это не просто "Unity, запущенный в браузере". Это место встречи двух экосистем: C#/Unity и JavaScript/TypeScript/npm.

Пока интеграция маленькая, `.jslib` достаточно. Но когда появляются async-вызовы, npm SDK, browser API, HTML template, ошибки, события и несколько независимых интеграций, прямые вызовы начинают превращаться в инфраструктурный долг.

Мой вывод после работы над JSPipe такой: для сложного Unity WebGL проекта нужно проектировать не отдельные JS-вызовы, а коммуникационный слой между runtime.

В моем случае этот слой получился таким:

- модули вместо глобальных функций;
- `Notify` для событий;
- `Call` для request/response;
- TypeScript/npm как нормальная часть проекта;
- разделение кода страницы и кода Unity runtime;
- сборка TS через WebGL build lifecycle;
- ошибки и пакеты как часть протокола, а не побочный эффект.

Когда этот слой есть, Unity WebGL перестает ощущаться как закрытая коробка, которую случайно положили на web-страницу. Он становится участником web-приложения.
